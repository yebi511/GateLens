## Purpose

为实时探测提供职责明确、数据只保存一次的结果协议，让调用方能够独立读取真实 HTTP 结果、各网关日志证据及确认关系，并识别采集缺口和未知归属，减少重复字段与多层状态解释带来的复杂度。

## ADDED Requirements

### Requirement: 探测结果具有唯一的日志与采集数据归属

探测查询 API MUST 仅在 `segments[].hops` 返回访问日志记录，MUST 仅在对应 Segment 的 `collection` 返回该网关采集状态。顶层 MUST NOT 输出旧的 `hops`、`collection`、`logSource`、`evidenceComplete` 或 `redirectSummary`。源 Agent 实际 HTTP 响应、实测耗时和请求错误 MUST 独立于分段日志保留；最终响应与最终上游引用 MUST 只能指向结果中存在的记录。网关、记录和重定向计数 MUST 能由分段记录及确认关系推导，不要求调用方读取重复记录列表。

#### Scenario: 单网关内部重定向
- **WHEN** 源 Agent 收到 HTTP 200，源网关包含一条 400 redirect 记录及一条后续 200 记录
- **THEN** 两条记录仅在该 Segment 返回一次，顶层保留 HTTP 200 及源 Agent 耗时，不返回已移除的重复字段

#### Scenario: 多网关与候选网关
- **WHEN** 探测关联两个有日志的网关及一个缺日志的候选网关
- **THEN** 每个网关独立返回记录和采集状态，调用方可以得到两个已观测网关、一个候选网关及各自记录数，不将候选网关当作已观测网关

#### Scenario: 无法归属最终上游
- **WHEN** 结果存在多个网关、多个无法区分的终止候选或相关证据缺口
- **THEN** 系统不提供无依据的最终上游引用，不使用记录列表末项兜底

### Requirement: Agent 仅返回所属网关的局部探测事实

Agent 探测命令结果 MUST 只包含命令对应的探测标识、所属网关局部日志、采集状态及问题；真实请求命令另包含实际 HTTP 结果，只读观测命令 MUST 不提供伪造的 HTTP 请求结果。Agent MUST NOT 返回联邦分段、联邦快照、全请求重定向摘要或全请求最终归属，Server MUST 负责组成查询 API 结果。

#### Scenario: 源请求命令
- **WHEN** Agent 执行真实 HTTP 探测
- **THEN** 命令结果包含实际响应或错误以及该网关局部采集结果，不包含联邦分段

#### Scenario: 其他网关只读观测
- **WHEN** Agent 执行同一探测 ID 的日志观测命令
- **THEN** 命令结果仅提供该网关局部证据，HTTP 请求结果缺省，且不发送额外请求

### Requirement: 问题按所属位置保存并提供稳定原因码

结果 MUST 使用结构化 `issues` 代替旧 `gaps` 和采集 `reasons`。每个问题 MUST 包含作用域、稳定原因码及说明，涉及具体上下文或记录时 MUST 带对应引用。执行层问题 MUST 只保存在顶层；采集、关系与候选推断问题 MUST 只保存在所属 Segment；同一问题 MUST NOT 为汇总而复制到其他层。状态判定 MUST 不依赖说明文本的关键词，展示汇总 MUST 能从所属列表按需生成。

#### Scenario: 日志轮转导致顺序未知
- **WHEN** 日志读取发现轮转，导致来源连续性无法确认
- **THEN** 所属 Segment 返回带稳定原因码的采集问题，关系保持未确认，顶层不复制该问题

#### Scenario: 窗口结束且后续记录缺失
- **WHEN** 采集窗口到期且只有 redirect 记录
- **THEN** 该 Segment 分别报告采集窗口结束和后续尝试缺失，两种问题可区分且不因跨层复制重复显示

#### Scenario: 修改说明措辞
- **WHEN** 同一个问题的说明文本改变而原因码不变
- **THEN** 尝试顺序判定、最终归属及汇总结果保持一致

### Requirement: 执行采集与关系状态相互独立

结果 MUST 独立提供整次探测执行状态、各网关日志采集状态及尝试关系状态。Segment MUST NOT 再输出与记录存在性重复的 `state` 和 `evidence`；是否已观测 MUST 根据记录存在性判断，候选依据 MUST 单独保留。采集稳定、已取得日志、内部关系明确及 HTTP 成功 MUST NOT 互相替代。无法确认的状态 MUST 有明确表达。

#### Scenario: HTTP 错误但采集稳定
- **WHEN** 源 Agent 收到 HTTP 503 且网关日志采集稳定
- **THEN** 请求可处于执行完成状态，响应仍为 HTTP 503，采集状态独立为稳定，不将响应改为成功

#### Scenario: HTTP 成功但关系未知
- **WHEN** 源 Agent 收到 HTTP 200，日志身份或顺序不足
- **THEN** 结果保留 HTTP 200，关系状态为未确认，且不宣称内部过程完整

### Requirement: 精简探测协议采用同步升级边界

探测 API 结果和 Agent 局部探测结果 MUST 显式提供 `schemaVersion: 2`。前端、Server、Agent MUST 同步切换；本次变更 MUST 不提供旧版结果的回退读取、双写或旧 Agent 适配。前端和 Server MUST 在消费结果时检查支持的协议版本，缺失或不支持的版本 MUST 明确报错，不得当作空日志或成功结果处理。探测 API 路径、入口选择和请求输入语义 MUST 保持现有行为。

#### Scenario: 新协议往返
- **WHEN** 同版本前端、Server 与 Agent 完成创建和查询探测
- **THEN** Agent 结果与 API 结果均带版本 2，创建与查询使用一致的精简结构

#### Scenario: 旧 Agent 回包
- **WHEN** Server 收到缺少版本或不支持版本的 Agent 探测结果
- **THEN** Server 明确报告探测协议不支持，不把旧字段映射为新结果或将其视为没有日志

#### Scenario: 前端收到旧结果
- **WHEN** 前端收到缺少版本或不支持版本的探测 API 结果
- **THEN** 页面报告协议版本不支持，不启用旧 `hops` 或旧分组回退

### Requirement: 固定取值字段具有一致且可校验的枚举契约

探测协议中由系统定义的执行状态、采集状态、尝试关系状态、关联方式、推断置信度、命令种类、问题作用域、问题原因码、归一化处理器结果及快照一致性 MUST 使用明确的有限取值集合。前端、Server 与 Agent MUST 对这些集合保持一致，序列化值 MUST 使用可读字符串，不使用与含义无关的数字序号。归一化探测 HTTP 方法与入口 Scheme MUST 保持现有允许值和默认行为。

消费方 MUST 校验有限取值字段；必填状态缺失、非法状态和非法问题码 MUST 明确报告非法结果，不得静默当作成功、已关联或精确匹配。已定义的 unknown 状态 MUST 保留对应未知语义；可选字段未提供 MUST 不自动升级为确定结果。来自日志或扩展配置的开放原始值 MUST 保留其可扩展性，不得因强制枚举丢失有效证据。

#### Scenario: 三端使用一致状态取值
- **WHEN** Agent 返回采集窗口结束状态，Server 输出精简结果，前端展示该结果
- **THEN** 三端均使用同一字符串 window-ended，并保持采集结束的业务含义，不依赖各处重复定义的近似状态

#### Scenario: 固定取值字段非法
- **WHEN** 版本有效的探测结果包含不支持的执行状态、采集状态、关联方式或问题原因码
- **THEN** 消费方明确报告非法结果，不把非法值解释为成功、已关联或没有问题

#### Scenario: 缺省关联与显式未知
- **WHEN** 有效结果未提供可选关联方式，或采集状态显式为 unknown
- **THEN** 系统分别按关联依据缺失或采集未知处理，不补造 probe-id 精确匹配，也不确认没有依据的最终归属

#### Scenario: 日志原始字段出现扩展值
- **WHEN** 匹配访问日志包含新的响应详情后缀、处理器业务原因码、协议名或 gRPC 状态文本
- **THEN** 系统保留这些原始值及该条日志，继续按明确 marker 规则和归一化结果表达证据，不因开放值未列入枚举而丢弃记录
