## Purpose

让实时探测页面清楚区分一次请求的最终 HTTP 结果、各网关的访问证据以及网关内的重定向尝试。用户能够看到中间失败和后续结果，同时理解日志未输出、顺序不确定、实际地址缺失与最终响应归属未知的边界，避免将最终成功理解为所有尝试均正常。

## ADDED Requirements

### Requirement: 独立展示请求结果和重定向提示

页面 MUST 在顶部使用源 Agent 实际响应码或请求错误展示请求结果，使用 Agent 实测请求耗时展示总耗时。存在内部重定向证据时 MUST 同时显示“发生内部重定向”及已观测重定向数量，MUST NOT 将中间 HTTP 400 覆盖到请求摘要或使用最终成功抹去中间错误。

页面 MUST 分开表达请求结果与过程证据状态；网关段、记录数和已观测重定向次数 MUST 分别计数，候选网关段 MUST 不计为已观测网关，记录数 MUST 不自动等于已确认尝试数，未收集过程 MUST 不宣称完整。

#### Scenario: 回退后请求成功
- **WHEN** Agent 收到 HTTP 200，网关内有两条关联记录，其中一条 HTTP 400 带内部重定向标记
- **THEN** 摘要显示 HTTP 200 与实测总耗时，同时显示内部重定向提示、两条记录及一次已观测重定向

#### Scenario: 请求失败但有中间日志
- **WHEN** Agent 请求超时或读取响应失败，但已获得 redirect 或普通访问日志
- **THEN** 摘要显示请求错误，并保留下方日志证据，不将某条 HTTP 200 日志替代 Agent 错误

#### Scenario: 已关联日志但过程状态未知
- **WHEN** 所有已显示网关段都有日志，但内部过程采集状态未知或存在关系缺口
- **THEN** 页面表达“已关联网关日志”与内部过程未知或存在缺口，不以绿色完整标记暗示所有内部尝试齐全

### Requirement: 网关段内展示内部尝试链

页面 MUST 保留现有输入表单与跨网关分段，在所属网关卡片内展示内部尝试；重定向 MUST 不额外增加网关跳数。已确认顺序的尝试 MUST 在本分组内编号，以连接说明表达“内部重定向，继续下一次尝试”；无法确认顺序时 MUST 使用记录名称及关系未确认提示，不输出确定的先后箭头。

尝试卡摘要 MUST 包含可用的 Provider、上游模型、Route 和响应码。redirect 记录 MUST 标为“中间响应”；非 redirect 记录 MUST 根据观察结果标为“终止尝试候选”或“最终响应”，不得仅凭 HTTP 200 自行升级归属。

#### Scenario: 单网关两个尝试
- **WHEN** 同一网关内存在有序的 400 redirect 记录与后续 200 记录
- **THEN** 页面在一个网关卡片内显示两次尝试及内部重定向连接说明，网关段数量保持一个

#### Scenario: 跨网关关联
- **WHEN** 两个网关共享本次 probe ID，并且各自包含 redirect 记录
- **THEN** 页面分别在所属网关卡片内展示尝试分组，不将不同网关的所有记录合并成一条内部尝试链

#### Scenario: 顺序存在歧义
- **WHEN** 观察结果报告记录关系或顺序未确认
- **THEN** 页面保留全部记录，并显示“同请求多条记录，关系未确认”及原因，不使用确定的尝试编号或因果连接

### Requirement: 按需展开尝试详情

页面 MUST 默认展开包含内部重定向或 HTTP 错误的网关尝试分组，普通单记录探测 MUST 保持紧凑展示。每条记录 MUST 提供可通过键盘操作的详情展开入口，展示既有 Route/upstream、响应详情、ext_proc、日志来源及关联依据。新增摘要 MUST 使用固定 AI 路由字段，不默认铺开包含问题和回答的完整 `ai_log`。

#### Scenario: 存在中间错误
- **WHEN** 结果包含失败后发生内部重定向的记录
- **THEN** 中间失败与后续尝试在首次呈现时可见，无需用户先展开整个网关分组

#### Scenario: 普通单记录与详情
- **WHEN** 结果仅有一条普通访问日志且 AI 摘要不存在
- **THEN** 页面仍紧凑显示 Route 和响应码，用户可展开既有 upstream 与 ext_proc 详情

### Requirement: 明确显示重定向证据缺口

页面 MUST 在对应网关卡片内显示内部过程缺口，并在请求证据区汇总。仅有 redirect 标记但无后续记录时 MUST 显示“已发生内部重定向，后续尝试记录缺失”；仅有同请求多条普通日志时 MUST 显示关系未确认，不得将其自动标为 redirect。采集结束、取消、读取错误和旧结果未知状态 MUST 按实际证据表达，不推断具体故障原因。

#### Scenario: 重定向后续缺失
- **WHEN** 采集结束后仅有 redirect 记录，且 Agent 实际响应为 HTTP 200
- **THEN** 页面同时保留 HTTP 200 请求结果和“后续尝试记录缺失”提示，不补造成功尝试卡片

#### Scenario: 普通记录关系未知
- **WHEN** 多条访问记录共享 probe ID，但没有 redirect 标记
- **THEN** 页面展示关联记录及关系未确认提示，不显示“一次重定向”

### Requirement: 展示最终上游的归属边界

页面 MUST 仅依据明确的响应归属结果显示全请求最终上游，MUST NOT 使用全局日志最后一条兜底。归属无法确定时 MUST 显示“最终上游归属未确认”，并保留各网关局部终止候选。实际地址为空或 `-` 时 MUST 显示“实际地址未记录”，不得将 Registry 或 Service 的配置目标冒充实际连接地址。

#### Scenario: 唯一可归属的源网关终止记录
- **WHEN** 观察结果明确报告源网关的唯一终止记录产生 Agent 收到的响应
- **THEN** 页面在该记录标注“最终响应”，并在上游区域展示其实际证据字段

#### Scenario: 多候选或跨网关归属未知
- **WHEN** 观察结果没有确定的全请求最终上游，但存在多个局部终止候选
- **THEN** 页面显示“最终上游归属未确认”，不因时间排序挑选其中一个

#### Scenario: cluster 已知但地址缺失
- **WHEN** 终止记录有 upstream cluster，而 `upstream_host` 为 `-`
- **THEN** 页面保留 cluster、Provider 和模型等可用字段，显示“实际地址未记录”，不展示确定的 Endpoint 或 Pod

### Requirement: 不混淆不同时间指标

页面 MUST 将 Agent 实测总耗时、单条访问日志的 `duration` 与 `upstream_service_time` 分开标注。重定向日志共享开始时间时 MUST 不将它们的 duration 相加，也 MUST 不用 duration 差值推算未记录的单次尝试耗时。

#### Scenario: 共享开始时间的 duration
- **WHEN** 两条日志共享 `start_time`，duration 分别为 440 ms 与 8736 ms
- **THEN** 详情分别显示两个日志 duration，顶部仅使用 Agent 实测总耗时，不显示总耗时 9176 ms 或推算出的尝试耗时 8296 ms

### Requirement: 兼容旧结果和窄屏交互

页面 MUST 在新增观察字段缺失时仍展示既有 `hops` 和 `segments`，将内部过程状态表达为未知，且不得恢复最后一条即最终上游的规则。窄屏时 MUST 在网关卡片内纵向排列尝试摘要和详情，长 Route、模型、cluster 与响应详情 MUST 可换行；成功、错误、redirect、未知状态 MUST 同时有文字标识，不仅使用颜色区分。

#### Scenario: 旧版结果
- **WHEN** 接口只返回既有探测字段
- **THEN** 页面正常展示日志记录及已有 ext_proc 证据，并显示内部过程状态未知

#### Scenario: 窄屏与键盘访问
- **WHEN** 用户在窄屏查看长 Route 的 redirect 链，并使用键盘展开尝试详情
- **THEN** 所有文字在卡片内可读，详情入口可聚焦和操作，各状态均有文字说明
